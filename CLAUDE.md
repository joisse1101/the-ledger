# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

A Streamlit app for viewing your local Claude Code sessions and projects. Top-nav-bar-navigated pages (Overview, Sessions, Projects). The Sessions page has two tables: "Live" (auto-polling, from the live process registry) and "All" (every session ever run, from on-disk transcripts, manual refresh).

## Setup & Run

```powershell
python -m venv .venv
.venv\Scripts\Activate.ps1
pip install -r requirements.txt
streamlit run app.py
```

The app opens at http://localhost:8501. `.streamlit/config.toml` sets `runOnSave = true`, so the app auto-reloads on file changes while `streamlit run` is active.

There are no lint, test, or build commands configured yet.

## Architecture

- `app.py` is the Streamlit entry point (run top-to-bottom on every interaction): just the top nav bar (`st.container(horizontal=True, ...)` row: title, "Overview"/"Sessions"/"Projects" buttons highlighted via `type="primary"` for the active page, a spacer column, and the dark-mode toggle), the process-wide dark-mode toggle logic, and dispatch to each page's render function via `st.session_state.page`. `st.divider()` below the nav bar has its height fixed at 2rem via `_COMPACT_LAYOUT_CSS` — note Streamlit 1.64 doesn't give dividers a dedicated testid, it's plain markdown (`[data-testid="stElementContainer"] > [data-testid="stMarkdown"] > [data-testid="stMarkdownContainer"] > hr`), so the CSS targets that `hr` directly; don't set `display: flex` on its `stMarkdownContainer` ancestor, since that collapses the `hr` (a block element with no intrinsic width) to 0px wide.
- Each page's own layout/render functions live in the `views/` package, one module per page (`views/overview.py`, `views/sessions.py`, `views/projects.py`), not in `app.py` — this keeps `app.py` limited to nav/theming/dispatch. It's named `views/` rather than `pages/` specifically to avoid colliding with Streamlit's own auto-detected multipage-app convention (a `pages/` directory next to the entry-point script gets an automatic sidebar nav), which this app doesn't use since it drives navigation itself via `st.session_state.page`.
- `claude_sessions.py` parses Claude Code's live session registry at `~/.claude/sessions/<pid>.json` (one file per Claude process; see a live example by reading any file in that directory). `load_sessions()` returns `ClaudeSession` dataclasses sorted by `updated_at` descending, with a module-level cache keyed by each file's mtime — unchanged files are served from cache instead of being re-read/re-parsed. Note: dead PIDs' files may linger, so entries aren't guaranteed to reflect live processes. Each session's `project` name is resolved the same way as `claude_transcripts.py`'s (and for the same reason — the live registry's own `cwd` can point below the real project root): `load_sessions()` looks up each session's `session_id` in `claude_transcripts.load_transcripts()` and reuses that transcript's already-resolved `project`, falling back to a `cwd`-derived guess when no matching transcript exists yet (e.g. a brand-new session with nothing written to disk yet).
- The Overview page (`render_overview_page` in `views/overview.py`), built from every on-disk transcript via `claude_transcripts.load_transcripts()`, opens with a `st.segmented_control` time-range filter (`_TIME_RANGES`: All time/Past week/Past month/Past quarter/Past year, applied by `_filter_transcripts_by_range` against each transcript's `started_at`) that scopes every chart and stat below it. Below that: a two-column row — a donut chart of session counts by project (`_render_project_sessions_chart`) on the left, a `_render_summary_stats()` panel of `st.metric` KPI tiles (in their own three-column grid) on the right (counts/session duration/cost) — followed by two full-width grouped-bar charts, "Messages & Cost by Project" and "Activity by Hour of Day" (`_render_messages_cost_chart` / `_render_hourly_activity_chart`, the latter fed by `_hourly_activity_dataframe`, which buckets each transcript's `started_at` by *local* hour via `.astimezone()` since the parsed timestamps are UTC). Both grouped-bar charts pair two measures on very different scales (messages vs. cost; sessions vs. messages) — rather than a literal dual-axis chart (flagged by the dataviz skill as the #1 charting mistake, since the alignment between two independent scales is arbitrary and invents a correlation that isn't in the data), each measure in a chart is normalized to % of its own peak (top project, or busiest hour) so both share one 0-100% axis; because "% of X" reads as ambiguous on its own, each chart has a `st.caption()` under its subheader spelling out what the normalization means. The three project-based charts (donut, "Messages & Cost by Project", and — via its `_project_color_scale()` domain — implicitly the hourly chart's palette too) all read from one shared `_project_totals_dataframe()` call, which folds sessions/messages/cost per project into the same top-`_MAX_PROJECT_SLICES` + "Other" split (ranked by session count), so a given project's color never shifts between charts; "Other" always gets the same muted `_MUTED_INK` regardless of theme. The grouped-bar charts instead color by *measure* (e.g. "Messages" vs. "Cost"), reusing the fixed categorical hue slots (`hues[0]`/`hues[1]`, via the shared `_theme_colors()` helper) — "Messages" is deliberately kept on `hues[0]` in both the project and hourly charts so that measure's color stays consistent across the page too. Colors come from a fixed-order categorical palette (`_CATEGORICAL_LIGHT`/`_CATEGORICAL_DARK`, chosen per `st_config.get_option("theme.base")`) documented by the dataviz skill's `references/palette.md` — the slot order must never be re-sorted per-chart, only which prefix of it is used may vary. The "Longest/shortest session" and "Most expensive/cheapest session" metrics carry a `help=` tooltip naming which project/session ID they refer to — the tooltip text renders as markdown, so the project/session-id line break needs a trailing two-space hard break (`f"{t.project}  \n{t.session_id}"`), since a bare `\n` gets collapsed.
- The Sessions page (`render_sessions_table` in `views/sessions.py`) is an `@st.fragment(run_every="2s")`, so it polls and redraws independently of the rest of the page. It has an "Auto-refresh" toggle (`st.session_state.auto_refresh`) and a "Last refreshed" caption laid out side by side in an `st.container(horizontal=True, vertical_alignment="center")` — when auto-refresh is off, the fragment still ticks on schedule but skips re-reading sessions and just redisplays the cached `st.session_state.sessions_df`.
- `claude_projects.py` parses Claude Code's global config at `~/.claude.json`, specifically its top-level `projects` map (one entry per directory Claude Code has been run/trusted in). `load_projects()` returns `ClaudeProject` dataclasses sorted by `last_start_time` descending, with a module-level cache keyed by the config file's mtime. Each entry reflects only that project's *last* session (no historical/cumulative data): trust status, last session ID, CLI version, cost, start time, lines added/removed, and any project-scoped MCP servers. `delete_project(project_path)` removes that project's entry from `~/.claude.json` (rewriting the file) and invalidates the cache; it doesn't touch on-disk transcripts.
- The Projects page (`render_projects_table` in `views/projects.py`) is a plain (non-fragment) render that caches its dataframe in `st.session_state.projects_df` and only re-reads `~/.claude.json` on first load or when the "⟳" reload button (paired with the "Last refreshed" caption in the same `st.container(horizontal=True, ...)` row) is clicked — no polling, unlike Sessions. A "Select rows to delete" toggle (`st.session_state.projects_delete_mode`) switches the plain `st.dataframe` for one with `on_select="rerun", selection_mode="single-row"` (keyed `"projects_table"`); selecting a row surfaces a delete button, which sets `st.session_state.confirm_delete_project` to show an inline "Confirm delete"/"Cancel" warning rather than deleting immediately. Confirming calls `_clear_project()`, which removes both the `~/.claude.json` entry (`delete_project`) and the project's on-disk transcripts (`delete_project_transcripts`), then re-reads `st.session_state.projects_df` and pops `"projects_table"` from session state to reset the selection (`.pop()`, not direct assignment — Streamlit raises `StreamlitWidgetAlreadyInstantiatedError` if you assign to a widget's key after it's already been instantiated in that same script run).
- `claude_transcripts.py` parses every on-disk session transcript at `~/.claude/projects/<sanitized-cwd>/<session-id>.jsonl` (one project folder per cwd, non-alphanumeric characters replaced with `-`; one `.jsonl` per session, one JSON object per line). Unlike the live registry, this covers every session that has ever run, including exited ones. `load_transcripts()` returns `ClaudeTranscript` dataclasses sorted by `updated_at` descending, with a module-level cache keyed by each file's mtime. Each transcript is built from a full line-by-line scan: `started_at`/`updated_at` are the min/max `timestamp` across all lines, `message_count` counts non-meta `user`/`assistant` lines, and `cost` sums per-turn token usage (`message.usage` on `type: "assistant"` lines) priced via the `_MODEL_PRICING` table in that file — a multi-block turn (e.g. thinking + tool_use) repeats the same `message.id` and its usage across several lines, so usage is counted once per unique `message.id`. This is an *estimate*: Claude Code doesn't write a dollar figure into the transcript anywhere (only `~/.claude.json`'s `lastCost` has one, and only for each project's most recent session), and an unrecognized model in `_MODEL_PRICING` is silently skipped rather than raising, so cost can undercount for sessions run on models missing from that table. Each transcript's `project` name isn't trusted from the jsonl's `cwd` field (a session can `cd` partway through, e.g. into a subdirectory, leaving `cwd` pointing somewhere below the real project root) — instead, `load_transcripts()` matches the transcript's actual on-disk parent folder against `sanitize_project_path(p.path)` for every `p` in `claude_projects.load_projects()`, so the displayed name always matches the Projects table; `project` only falls back to a `cwd`/folder-derived guess when no project entry matches (e.g. it's since been deleted). `delete_project_transcripts(cwd)` matches transcripts by their recorded `cwd` field (not by re-deriving the directory-sanitization scheme) and `shutil.rmtree`s their parent directory/directories; `delete_transcript(session_id)` deletes a single transcript's `.jsonl` file. Both remove the affected paths from the mtime cache directly rather than waiting for the next `load_transcripts()` scan to notice they're gone.
- The "All" sessions table (`render_transcripts_table` in `views/sessions.py`, under the Sessions page below "Live") follows the same manual-refresh pattern as Projects (caches in `st.session_state.transcripts_df`, "⟳" button, no polling) rather than the Sessions fragment's auto-poll — a full transcript scan is too expensive to run every 2s. It has the same "Select rows to delete" toggle/`st.dataframe` `on_select` pattern as Projects, but with `selection_mode="multi-row"` (key `"transcripts_table"`) since individual sessions, not whole projects, are deleted here via `delete_transcript`. Live sessions (cross-referenced by session ID against `load_sessions()`) can't be deleted: Streamlit's dataframe/data_editor widgets only support disabling an entire column, not individual rows/cells, so instead of a disabled checkbox, any live session included in the selection is silently filtered out of the delete action and called out in a caption ("N selected session(s) are still live and can't be deleted").
- `.streamlit/config.toml` holds Streamlit config (theme, server settings). `.streamlit/secrets.toml`, if created, is gitignored — put secrets there, accessed via `st.secrets`.
- The top nav bar's "Dark mode" toggle (`main()` in `app.py`) flips the live theme by calling `streamlit.config.set_option("theme.base", ...)` and `st.rerun()` — an undocumented mechanism (Streamlit has no supported per-session theme API), and one that's process-wide: since `theme.base` is a module-level global, toggling it in one browser tab also re-themes any other tab connected to the same running server. Acceptable for this single-user local tool; not safe to reuse if this app is ever served to multiple concurrent users. The toggle's on-disk persistence lives in `.streamlit/theme_pref.json` (`_load_theme_pref`/`_persist_theme` in `app.py`), a gitignored JSON file read once per new session to seed the toggle's initial value — this is deliberately *not* written into the checked-in `.streamlit/config.toml`, so a user's local preference doesn't show up as repo churn; `config.toml`'s `theme.base` stays the neutral fallback for a machine with no pref file yet.
- `requirements.txt` currently lists `streamlit` and `pandas` (unpinned — `st.fragment(run_every=...)` requires Streamlit ≥1.37). The installed version in `.venv` is Streamlit 1.64.0 — check this line before assuming a feature/API is unavailable instead of re-running `pip show streamlit`.
- `hooks/` is a standalone utility, unrelated to the Streamlit app: Windows toast notifications for Claude Code's `Notification`/`Stop` hook events, with `Install-ClaudeHooks.ps1`/`Uninstall-ClaudeHooks.ps1` to set them up on a machine. See `hooks/README.md` for how it works and full install/uninstall/test steps.

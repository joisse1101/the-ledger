# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

A Streamlit app for viewing your local Claude Code sessions and projects. Top-nav-bar-navigated pages (Overview, Sessions, Projects). The Sessions page has two tables: "Live" (auto-polling, from the live process registry) and "All" (every session ever run, from on-disk transcripts, manual refresh).

## Setup & Run

```powershell
python -m venv .venv
.venv\Scripts\Activate.ps1
pip install -r requirements.txt
streamlit run app.py
```

The app opens at http://localhost:8501. `.streamlit/config.toml` sets `runOnSave = true`, so the app auto-reloads on file changes while `streamlit run` is active.

A `.venv` already exists at the repo root with dependencies installed — activate it (`.venv\Scripts\Activate.ps1`, or invoke `.venv\Scripts\python.exe` / `.venv\Scripts\pytest.exe` directly) rather than searching for or recreating one.

## Testing

```powershell
pip install -r requirements-dev.txt  # installs requirements.txt + pytest
pytest
```

Tests live in `tests/` (`pyproject.toml` sets `pythonpath = ["."]` and `testpaths = ["tests"]`), one file per module under test, covering the pure parsing/aggregation logic (`claude_db._message_cost`, `views/overview.py`'s time-range filtering and chart data prep, etc.) and the SQLite read/write/delete paths in `claude_db.py`/`claude_projects.py`/`claude_transcripts.py`. `tests/conftest.py`'s `isolated_db` fixture monkeypatches `claude_db.db_path`/`config_path`/`projects_dir` to a `tmp_path`, so the suite never touches the real `~/.claude.json` or `~/.claude/projects/`. Streamlit rendering (the `render_*` functions that call `st.*` widgets) isn't covered — only the plain functions those pages build their data from (e.g. `_projects_dataframe`, `_sessions_dataframe`).

## Architecture

- `app.py` is the Streamlit entry point (run top-to-bottom on every interaction): the top nav bar (`st.container(horizontal=True, ...)` row: title, "Overview"/"Sessions"/"Projects" buttons highlighted via `type="primary"` for the active page, a spacer column, the dark-mode toggle, and a single "⟳" refresh button + "Last refreshed: HH:MM:SS" caption), the process-wide dark-mode toggle logic, seeding `claude_db`'s SQLite snapshot on the very first run (`if claude_db.refreshed_at() is None: claude_db.refresh()`, so the nav bar and pages aren't empty before anyone's clicked refresh), and dispatch to each page's render function via `st.session_state.page`. The "⟳" button calls `claude_db.refresh()`; the caption reads `claude_db.refreshed_at()` *after* that button's click is handled, so a click's new timestamp shows in that same script run instead of lagging one click behind. The same refresh also fires automatically every 10 minutes via `_auto_refresh_data()`, an invisible `@st.fragment(run_every="10m")` called once per script run from `main()`. Because that call happens on *every* rerun (page nav, dark-mode toggle, ...) and not just the fragment's own 10m timer, the fragment body can't unconditionally `refresh()` + `st.rerun()` — doing so on the very first call would `st.rerun()` (default `scope="app"`) straight back into `main()`, which calls the fragment again, looping forever. `_auto_refresh_due(last, now)` (a plain, unit-tested function — see `tests/test_app.py`) gates this: it tracks the last auto-refresh time in `st.session_state["_last_auto_refresh"]` and only returns `True` once `_AUTO_REFRESH_INTERVAL` (10 minutes) has actually elapsed, so most calls are a no-op and only one call per interval does the refresh + full-app rerun. Like the manual button, this only runs while a browser tab has the app open — Streamlit fragments don't tick with no client connected — and it's 10 minutes from tab load, not aligned to the wall-clock half-hour. This single button/caption pair replaces what used to be two separate "⟳" buttons/captions on the Projects and "All" sessions tables — since all three pages now read from one shared SQLite snapshot (see `claude_db.py`) instead of each independently re-reading its own file(s), one shared control in the nav bar refreshes all of them at once. `st.divider()` below the nav bar has its height fixed at 2rem via `_COMPACT_LAYOUT_CSS` — note Streamlit 1.64 doesn't give dividers a dedicated testid, it's plain markdown (`[data-testid="stElementContainer"] > [data-testid="stMarkdown"] > [data-testid="stMarkdownContainer"] > hr`), so the CSS targets that `hr` directly; don't set `display: flex` on its `stMarkdownContainer` ancestor, since that collapses the `hr` (a block element with no intrinsic width) to 0px wide.
- Each page's own layout/render functions live in the `views/` package, one module per page (`views/overview.py`, `views/sessions.py`, `views/projects.py`), not in `app.py` — this keeps `app.py` limited to nav/theming/dispatch. It's named `views/` rather than `pages/` specifically to avoid colliding with Streamlit's own auto-detected multipage-app convention (a `pages/` directory next to the entry-point script gets an automatic sidebar nav), which this app doesn't use since it drives navigation itself via `st.session_state.page`.
- `claude_db.py` is the single SQLite-backed store that `claude_projects.py` and `claude_transcripts.py` both read from, rather than each independently scanning and mtime-caching its own file(s) on disk as they used to. All of that disk-reading — `~/.claude.json` and `~/.claude/projects/*/*.jsonl` parsing, the `_MODEL_PRICING` table, `sanitize_project_path()`, etc. — now lives here. `refresh()` rescans both sources, resolves each transcript's `project` from the just-scanned project list (matching the transcript's on-disk parent folder against `sanitize_project_path()`, same as before), replaces the `projects`/`transcripts` tables' contents in one pass, and stamps a `meta.refreshed_at` timestamp; `refreshed_at()` reads that timestamp back. This is the *only* place disk gets rescanned — triggered explicitly (the nav bar's "⟳" button), plus once automatically via `startup()` on process start, not on every page render or any polling interval. `startup()` (called once from `app.py`'s `main()`, guarded by a module-level flag so later Streamlit reruns in the same process are no-ops) treats the database as a pure derived cache rather than something to migrate forward: it deletes any `.streamlit/ledger.db` left over from a previous run — sidestepping any schema-migration logic entirely, since a leftover file is just wiped instead of ALTER-TABLE'd — calls `refresh()` to rebuild it from disk, and registers an `atexit` handler to delete the file again on process exit (best-effort; a hard kill skips it, but the next `startup()` wipes it anyway). `claude_projects.load_projects()` / `claude_transcripts.load_transcripts()` just `SELECT * ... ORDER BY` these tables and build dataclasses from the rows — cheap enough to call fresh on every script rerun with no caching of their own. `delete_project()` / `delete_project_transcripts()` / `delete_transcript()` each mutate the real on-disk source first, then delete just the matching row(s) from SQLite by key (`delete_project_row`/`delete_transcript_rows_by_cwd`/`delete_transcript_row`) rather than calling `refresh()` again — a full rescan isn't needed here because delete has no derivation ambiguity (the key just removed from disk is exactly the key to remove from the db), and skipping it avoids re-parsing every transcript file on every delete. The tradeoff: those two writes (disk, then db) aren't atomic, so a crash in between would leave a stale db row until the next `refresh()` — acceptable for a single-user local tool where deletes are rare and already gated behind a confirm dialog. The database file (`.streamlit/ledger.db`) is gitignored like `theme_pref.json`, since it's a derived local cache, not project data.
- `claude_sessions.py` parses Claude Code's live session registry at `~/.claude/sessions/<pid>.json` (one file per Claude process; see a live example by reading any file in that directory) directly from disk on every call — unlike projects/transcripts, this isn't routed through `claude_db.py`, since the "Live" table polls it every 2s and a snapshot refreshed only on demand would defeat that. `load_sessions()` returns `ClaudeSession` dataclasses sorted by `updated_at` descending, with its own module-level cache keyed by each file's mtime — unchanged files are served from cache instead of being re-read/re-parsed. Note: dead PIDs' files may linger, so entries aren't guaranteed to reflect live processes. Each session's `project` name is resolved by looking up its `session_id` in `claude_transcripts.load_transcripts()` (now a cheap SQLite query rather than a full jsonl rescan) and reusing that transcript's already-resolved `project`, falling back to a `cwd`-derived guess when no matching transcript exists yet (e.g. a brand-new session with nothing written to disk yet).
- `claude_context.py` reads a live session's token usage straight from its transcript, outside `claude_db.py`/SQLite for the same reason `claude_sessions.py` is: the Live table polls every 2s and an on-demand snapshot would be stale (and blank for a brand-new session no other page knows yet). The transcript is located from the registry's `cwd` and session ID (`claude_db.projects_dir() / sanitize_project_path(cwd) / <session-id>.jsonl`), falling back to one memoized `*/<session-id>.jsonl` glob. **Context** is the latest real main-thread assistant turn's `input + cache_read + cache_creation` tokens — "real" meaning not `isSidechain`, model not `<synthetic>` (API-error placeholders), non-zero usage, de-duplicated by `message.id` (last line's usage wins, but `tool_use` blocks accumulate across the lines of a multi-block turn). `live_context()` tail-reads backwards from EOF in a window that starts at 256 KB and doubles until 24 real turns are found or the file start is reached (dropping the first line when the window began mid-file; unparseable/partial lines are skipped), memoized by `(path, size, mtime_ns)` so an idle session costs one `stat`; it returns a `LiveContext(size, growth, history)` or `None` and never raises (~10 ms cold on the 10 MB transcript, ~0.03 ms cached). `format_context()` renders `394k ▲ +2.1k ▁▂▃…`: `humanise_tokens` (exact below 1,000, nearest thousand + `k` below 1M, one decimal + `M` above — keep in step with the `toast-token-usage` change) for sizes, one-decimal `k` for growth deltas, and a block-glyph sparkline scaled from 0 (not the window minimum) to the window max so slow growth reads as flat. Deliberately no percentage/model-window/threshold anywhere — nothing in the transcript defines them. For the detail dialog, `load_detail()` fully parses the transcript on demand (memoized by the same stat key, so not re-parsed on the 2s tick) into per-turn records plus `compact_boundary` compactions; a cache miss is any turn but the first that wrote more cache than it read; growth attribution credits the context delta at turn *t* to the first tool called in turn *t−1* (or "prompt / text"), over the segment since the latest compaction, using signed deltas so `first-turn context + attributed growth == current context` holds exactly. Main thread only — subagent transcripts (`<session-id>/subagents/`) have their own contexts and are ignored, so these numbers won't line up with `cost-state` totals.
- The Overview page (`render_overview_page` in `views/overview.py`), built from every transcript in the SQLite snapshot via `claude_transcripts.load_transcripts()`, opens with a `st.segmented_control` time-range filter (`_TIME_RANGES`: All time/Today/Yesterday/Past week/Past month/Past quarter/Past year) that scopes every chart and stat below it. `_TIME_RANGES` maps each label to an inclusive `(oldest_days_ago, newest_days_ago)` pair (`None` for "All time", which skips filtering) rather than a plain day count, since most ranges run up to today (`newest_days_ago=0`, e.g. "Past week" = `(6, 0)`) but "Yesterday" is a single day that excludes today (`(1, 1)`). `_filter_transcripts_by_range` applies this against each transcript's `started_at` (falling back to `updated_at`), and deliberately buckets by *local calendar date* (`anchor.astimezone().date()`) rather than a rolling `now - N*24h` window, so e.g. "Today" always means every session started on today's local date regardless of what time it is right now, not "the last 24 hours". Below that: a two-column row — a donut chart of session counts by project (`_render_project_sessions_chart`) on the left, a `_render_summary_stats()` panel of `st.metric` KPI tiles (in their own three-column grid) on the right (counts/session duration/cost) — followed by two full-width grouped-bar charts, "Messages & Cost by Project" and "Activity by Hour of Day" (`_render_messages_cost_chart` / `_render_hourly_activity_chart`, the latter fed by `_hourly_activity_dataframe`, which buckets each transcript's `started_at` by *local* hour via `.astimezone()` since the parsed timestamps are UTC, then trims the output to the contiguous range of hours that actually have activity rather than always showing all 24). Both grouped-bar charts pair two measures on very different scales (messages vs. cost; sessions vs. messages) — rather than a literal dual-axis chart (flagged by the dataviz skill as the #1 charting mistake, since the alignment between two independent scales is arbitrary and invents a correlation that isn't in the data), each measure in a chart is normalized to % of its own peak (top project, or busiest hour) so both share one 0-100% axis; because "% of X" reads as ambiguous on its own, each chart has a `st.caption()` under its subheader spelling out what the normalization means. The three project-based charts (donut, "Messages & Cost by Project", and — via its `_project_color_scale()` domain — implicitly the hourly chart's palette too) all read from one shared `_project_totals_dataframe()` call, which folds sessions/messages/cost per project into the same top-`_MAX_PROJECT_SLICES` + "Other" split (ranked by session count), so a given project's color never shifts between charts; "Other" always gets the same muted `_MUTED_INK` regardless of theme. The grouped-bar charts instead color by *measure* (e.g. "Messages" vs. "Cost"), reusing the fixed categorical hue slots (`hues[0]`/`hues[1]`, via the shared `_theme_colors()` helper) — "Messages" is deliberately kept on `hues[0]` in both the project and hourly charts so that measure's color stays consistent across the page too. Colors come from a fixed-order categorical palette (`_CATEGORICAL_LIGHT`/`_CATEGORICAL_DARK`, chosen per `st_config.get_option("theme.base")`) documented by the dataviz skill's `references/palette.md` — the slot order must never be re-sorted per-chart, only which prefix of it is used may vary. The "Longest/shortest session" and "Most expensive/cheapest session" metrics carry a `help=` tooltip naming which project/session ID they refer to — the tooltip text renders as markdown, so the project/session-id line break needs a trailing two-space hard break (`f"{transcript.project}  \n{transcript.session_id}"`), since a bare `\n` gets collapsed.
- The Sessions page's "Live" table (`render_sessions_table` in `views/sessions_live.py`) is an `@st.fragment(run_every="2s")`, so it polls and redraws independently of the rest of the page. It has an "Auto-refresh" toggle (`st.session_state.auto_refresh`) and a "Last refreshed" caption laid out side by side in an `st.container(horizontal=True, vertical_alignment="center")` — when auto-refresh is off, the fragment still ticks on schedule but skips re-reading sessions and just redisplays the cached `st.session_state.sessions_df`. Each row has a "Context" cell (`_context_cell` in `views/sessions_data.py`, formatted by `claude_context.format_context`, `--` when unavailable or when reading that one session raises) and a hidden `CWD` field. Clicking a row opens the context detail dialog (`views/sessions_context.py`, see `claude_context.py` below): an `st.dialog` driven by `st.session_state.context_dialog_info` and re-invoked at the end of every fragment run while that state is set. Spiked and confirmed to stay open, keep its scroll position and update in place across the fragment's 2s reruns, so no inline-panel fallback is needed. Only one dialog can be open per script run, so `_open_context_dialog` clears the All table's `recap_dialog_info` and `_open_session_dialog` clears `context_dialog_info`. The dialog shows a stacked-bar Vega-Lite chart of tokens per response (cache read / cache written / new, with a ▼ on cache-miss responses and a dashed rule on the first response after a compaction — themed via `views/overview.py`'s `_theme_colors()`), an "All responses" table with the four token counts and a Note column, and "What filled the context" (by-tool growth table plus the five largest single increases). Everything is absolute tokens; nothing is shown as a percentage of a limit.
- `claude_projects.py` holds the `ClaudeProject` dataclass and the query/delete functions for Claude Code's project data (originally `~/.claude.json`'s top-level `projects` map — one entry per directory Claude Code has been run/trusted in, reflecting only that project's *last* session: trust status, last session ID, CLI version, cost, start time, lines added/removed, and any project-scoped MCP servers; the actual `~/.claude.json` parsing now lives in `claude_db.py`, see above). `load_projects()` queries `claude_db.fetch_projects()` and builds dataclasses from the rows, sorted newest-started first. `delete_project(project_path)` still edits `~/.claude.json` directly (that's the real source of truth) and then removes the matching row from SQLite via `claude_db.delete_project_row()`; it doesn't touch on-disk transcripts.
- The Projects page (`render_projects_table` in `views/projects.py`) is a plain (non-fragment) render with no polling and no `st.session_state` dataframe caching of its own — `_projects_dataframe()` re-queries `claude_projects.load_projects()` fresh on every script rerun, cheap now that it's a SQL query rather than a `~/.claude.json` re-parse. (The "⟳ Refresh"/"Last refreshed" control that repopulates the underlying data now lives once in the nav bar — see `app.py` — not on this page.) A "Edit mode" toggle (`st.session_state.projects_delete_mode`) switches the plain `st.dataframe` for one with `on_select="rerun", selection_mode="single-row"` (keyed `"projects_table"`); selecting a row surfaces a delete button, which sets `st.session_state.confirm_delete_project` to show an inline "Confirm delete"/"Cancel" warning rather than deleting immediately. Confirming calls `_clear_project()`, which removes both the `~/.claude.json` entry (`delete_project`) and the project's on-disk transcripts (`delete_project_transcripts`) — each already updates the SQLite snapshot directly (see `claude_db.py`), so the next `_projects_dataframe()` call reflects the deletion with no extra refresh needed — then pops `"projects_table"` from session state to reset the selection (`.pop()`, not direct assignment — Streamlit raises `StreamlitWidgetAlreadyInstantiatedError` if you assign to a widget's key after it's already been instantiated in that same script run).
- `claude_transcripts.py` holds the `ClaudeTranscript` dataclass and the query/delete functions for session transcript data (originally parsed line-by-line from `~/.claude/projects/<sanitized-cwd>/<session-id>.jsonl` — one project folder per cwd, non-alphanumeric characters replaced with `-`; unlike the live registry, this covers every session that has ever run, including exited ones; the actual jsonl parsing now lives in `claude_db.py`'s `refresh()`, see above). That parsing derives `started_at`/`updated_at` as the min/max line timestamp, `message_count` from non-meta `user`/`assistant` lines, `context` (the same latest-real-main-thread-turn `input + cache_read + cache_creation` figure `claude_context.py` shows live, via `claude_db._context_tokens` — a deliberate copy of its "real turn" rule, since `claude_context` imports `claude_db`; `tests/test_claude_db.py` asserts the two agree; NULL when a transcript has no real turn, shown as `--` in the All table's numeric, sortable "Context" column via `views/sessions_table.py`'s `_format_context`), `cost` by summing per-turn `message.usage` priced via `_MODEL_PRICING` (counted once per unique `message.id`, since a multi-block turn repeats it), and `project` by matching the transcript's on-disk parent folder against each project's `sanitize_project_path()` rather than trusting the jsonl's own `cwd` (which can point below the real project root if a session `cd`s partway through) — falling back to a `cwd`/folder-derived guess only when no project entry matches. Cost is an *estimate*: Claude Code doesn't write a dollar figure into the transcript anywhere, and an unrecognized model in `_MODEL_PRICING` is silently skipped rather than raising. `load_transcripts()` here just queries `claude_db.fetch_transcripts()` and builds dataclasses, sorted newest-updated first. `delete_project_transcripts(cwd)` and `delete_transcript(session_id)` look up the affected path(s) via `claude_db` (`transcript_paths_for_cwd`/`transcript_path_for_session`), `shutil.rmtree`/`unlink` the real file(s) on disk, then delete just those rows from SQLite — the same targeted-delete pattern as `claude_projects.delete_project` (see `claude_db.py`'s note on why a full rescan isn't needed for deletes).
- The "All" sessions table (`render_transcripts_table` in `views/sessions.py`, under the Sessions page below "Live") is a plain render like Projects — no polling, no dataframe caching of its own; `_transcripts_dataframe()` re-queries `claude_transcripts.load_transcripts()` fresh each rerun, which is cheap now that it's a SQL query rather than the full transcript-file scan this used to require (the reason it never ran on the Sessions fragment's 2s cadence, and — like Projects — used to have its own manual refresh button; that's now the single shared control in the nav bar). It has the same "Edit mode" toggle/`st.dataframe` `on_select` pattern as Projects, but with `selection_mode="multi-row"` (key `"transcripts_table"`) since individual sessions, not whole projects, are deleted here via `delete_transcript`. Live sessions (cross-referenced by session ID against `load_sessions()`) can't be deleted: Streamlit's dataframe/data_editor widgets only support disabling an entire column, not individual rows/cells, so instead of a disabled checkbox, any live session included in the selection is silently filtered out of the delete action and called out in a caption ("N selected session(s) are still live and can't be deleted").
- `.streamlit/config.toml` holds Streamlit config (theme, server settings). `.streamlit/secrets.toml`, if created, is gitignored — put secrets there, accessed via `st.secrets`. `.streamlit/ledger.db` (the SQLite snapshot from `claude_db.py`) is likewise gitignored, as a derived local cache rather than project data.
- The top nav bar's "Dark mode" toggle (`main()` in `app.py`) flips the live theme by calling `streamlit.config.set_option("theme.base", ...)` and `st.rerun()` — an undocumented mechanism (Streamlit has no supported per-session theme API), and one that's process-wide: since `theme.base` is a module-level global, toggling it in one browser tab also re-themes any other tab connected to the same running server. Acceptable for this single-user local tool; not safe to reuse if this app is ever served to multiple concurrent users. The toggle's on-disk persistence lives in `.streamlit/theme_pref.json` (`_load_theme_pref`/`_persist_theme` in `app.py`), a gitignored JSON file read once per new session to seed the toggle's initial value — this is deliberately *not* written into the checked-in `.streamlit/config.toml`, so a user's local preference doesn't show up as repo churn; `config.toml`'s `theme.base` stays the neutral fallback for a machine with no pref file yet.
- `requirements.txt` currently lists `streamlit` and `pandas` (unpinned — `st.fragment(run_every=...)` requires Streamlit ≥1.37). The installed version in `.venv` is Streamlit 1.64.0 — check this line before assuming a feature/API is unavailable instead of re-running `pip show streamlit`.
- `hooks/` is a standalone utility, unrelated to the Streamlit app: Windows toast notifications for Claude Code's `Notification`/`Stop` hook events, with `Install-ClaudeHooks.ps1`/`Uninstall-ClaudeHooks.ps1` to set them up on a machine. See `hooks/README.md` for how it works and full install/uninstall/test steps.
